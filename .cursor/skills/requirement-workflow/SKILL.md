# 需求开发流程编排器

## 目的

作为需求开发的端到端编排器，引导用户和AI完成从需求输入到审批通过的完整前置流程，确保每个功能都经过充分的分析和评估后再进入开发阶段。

## 使用场景

**强制使用场景**：
- 所有新功能开发
- 修改现有核心系统
- 跨模块的功能开发

**可选使用场景**（仍建议执行）：
- 简单功能添加（< 50行代码）
- 独立工具类开发

**豁免场景**：
- 简单Bug修复（< 10行代码）
- 配置文件调整
- UI文案修改
- 纯资源替换

## 触发方式

```
@requirement-workflow
需求: [需求描述]
模块: [所属模块，可选]
```

简写触发：
```
@requirement-workflow 开发一个背包系统
```

## 完整工作流程

```
用户提出需求
    |
    v
阶段0: Context 检查与沉淀 ⭐ 新增
    |
    +-- 无 Context → 调用 @project-context-analyzer 沉淀
    |
    +-- 有 Context → 读取并理解项目框架
    |
    v
阶段1: 需求理解与信息缺口识别
    |
    v
阶段2: 生成标准需求卡片
    |
    v
阶段3: Skills功能白名单检查
    |
    v
阶段4: 架构设计分析（调用 @architecture-design-analyzer）
    |
    v
阶段5: 影响面分析（调用 @impact-scope-analyzer）
    |
    v
阶段6: 生成审批报告
    |
    v
用户审批决策
    |
    +-- 通过 --> 进入开发阶段
    +-- 驳回 --> 回到阶段1或终止
```

## 阶段0：Context 检查与沉淀 ⭐

**目标**：确保有项目上下文（Context）可供参考，这是后续所有分析的基础。

**操作**：
1. 检查 `context/index.md` 文件是否存在
2. 如不存在 → 提示用户先沉淀 Context
3. 如存在 → 读取 Context 并理解项目框架

### Context 检查流程

```
检查 context/index.md
    │
    ├── 不存在 ──→ 提示用户运行 @project-context-analyzer
    │               "检测到项目尚未沉淀 Context，建议先运行 @project-context-analyzer 分析项目框架，这将帮助我更准确地理解现有架构。"
    │
    └── 存在 ────→ 读取 Context
                    ├── 读取 context/index.md 获取项目概览
                    ├── 根据需求识别相关模块
                    └── 读取 modules/[相关模块].md
```

### Context 复用格式

在需求理解阶段，AI 应引用 Context：

```
📋 基于 Context 的需求理解

根据项目 Context 分析：
- 项目架构: [从 context/index.md 读取]
- 涉及模块: [识别的相关模块]
- 现有类似功能: [从模块文档发现]

[然后继续原有的需求理解流程...]
```

### 首次使用项目

**场景**：用户首次在新项目上使用本工作流

**处理**：
```
AI：欢迎！检测到这是首次在此项目上使用需求开发流程。

为了更准确地理解项目架构和提供建议，建议先沉淀项目 Context。

选项：
1. 运行 @project-context-analyzer 分析项目框架（推荐，约5-10分钟）
2. 跳过，直接进行需求开发（后续仍可补充）

您的选择？

用户：1
→ 调用 @project-context-analyzer 执行分析

用户：2
→ 继续流程，但记录建议后续补充 Context
```

**确认点**：确认已读取或已提示沉淀 Context。

## 阶段1：需求理解与信息缺口识别（基于业务上下文）

**目标**：在充分理解现有业务的基础上分析需求，识别需求与现有功能的关系，消除不确定性。

**核心理念**：**所有需求都是基于现有功能的迭代，不能脱离业务凭空分析**

---

### 步骤1：基于 Context 分析现有业务

**操作**：在理解新需求前，先基于 Context 梳理相关现有功能。

**分析维度**：

| 分析项 | 说明 | 数据来源 |
|--------|------|----------|
| 所属模块现状 | 该模块目前已有什么功能 | context/modules/[模块].md |
| 功能相似性 | 是否有类似功能可复用/扩展 | context/index.md |
| 依赖关系 | 新功能与现有功能的依赖 | context/architecture/dependency-graph.md |
| 架构约束 | 现有架构对新功能的约束 | context/architecture/decisions.md |

**输出格式**：
```
📋 现有业务分析（基于 Context）

目标模块: [模块名]
模块现状:
- 现有核心功能:
  1. [功能A] - [一句话描述]
  2. [功能B] - [一句话描述]
- 公共接口: [关键接口列表]

功能相似性分析:
- 发现类似功能: [现有功能X]（相似度: [高/中/低]）
- 可复用组件: [组件A], [组件B]
- 需要扩展的点: [扩展点描述]

依赖关系:
- 上游依赖（新功能依赖谁）: [模块A], [模块B]
- 下游影响（谁会依赖新功能）: [模块C]

架构约束:
- 现有设计模式: [模式名称]
- 技术选型限制: [限制说明]
- 性能基线要求: [性能指标]
```

---

### 步骤2：需求类型判定

**操作**：明确新需求与现有功能的关系类型。

**需求类型分类**：

| 类型 | 定义 | 典型特征 | 分析重点 |
|------|------|----------|----------|
| **新增功能** | 全新功能，现有系统没有 | 新模块、新机制 | 与现有架构的兼容性 |
| **功能扩展** | 在现有功能上增加能力 | 已有模块新增接口 | 接口兼容性、向后兼容 |
| **功能优化** | 改进现有功能体验/性能 | 不改变核心逻辑 | 回归风险、性能基准 |
| **功能重构** | 重写现有功能，行为不变 | 代码结构调整 | 行为一致性、影响面 |
| **Bug修复** | 修复现有功能缺陷 | 问题描述+复现路径 | 修复范围、副作用 |

**输出格式**：
```
📋 需求类型判定

需求描述: [用户原始需求]

类型判定: [新增功能/功能扩展/功能优化/功能重构/Bug修复]

判定理由:
- [分析点1]
- [分析点2]

与现有功能的关系:
├── 如果是新增功能
│   └── 需要与[现有功能A]集成
│   └── 需要遵循[现有模块B]的接口规范
│
├── 如果是功能扩展
│   └── 在[现有功能X]基础上增加[新能力]
│   └── 需要修改[接口A]增加参数
│
└── 如果是功能优化
    └── 优化[现有功能Y]的[性能/体验]
    └── 保持现有接口不变
```

**确认点**：用户确认需求类型判定是否准确。

---

### 步骤3：基于业务上下文的需求理解

**操作**：在现有业务基础上，分析新需求的具体内容。

**分析框架**：

```
新需求分析必须回答：
┌─────────────────────────────────────────────────────────┐
│ 1. 为什么需要这个功能？（业务价值）                       │
│    → 解决什么痛点？提升什么指标？                        │
├─────────────────────────────────────────────────────────┤
│ 2. 与现有功能如何配合？（集成点）                         │
│    → 调用哪些现有接口？触发哪些现有事件？                 │
├─────────────────────────────────────────────────────────┤
│ 3. 会改变现有功能的什么？（变更点）                       │
│    → 接口变化？行为变化？数据格式变化？                   │
├─────────────────────────────────────────────────────────┤
│ 4. 需要现有功能提供什么支持？（依赖）                     │
│    → 需要现有模块暴露新接口？提供新事件？                 │
├─────────────────────────────────────────────────────────┤
│ 5. 对现有功能有什么约束？（限制）                         │
│    → 性能不能下降？兼容性要求？                          │
└─────────────────────────────────────────────────────────┘
```

**输出格式**：
```
📋 需求理解确认（基于业务上下文）

【业务背景】
现有模块: [模块名]
相关现有功能: [功能A], [功能B]
需求类型: [新增/扩展/优化/重构]

【需求目标】
功能目标: [AI对需求的理解]
业务价值: [解决什么问题/提升什么指标]

【与现有功能的集成】
需要调用的现有接口:
- [接口1] - [用途]
- [接口2] - [用途]

需要触发的现有事件:
- [事件1] - [触发时机]

【对现有功能的影响】
接口变更:
- [接口A] 需要增加参数 [参数名]
- [接口B] 返回值格式需要调整

行为变更:
- [功能X] 的 [行为] 将会改变
- [功能Y] 需要增加对新功能的支持

【需要澄清的问题】
❓ [问题1] - 关于与[现有功能A]的集成方式
  选项: 1) [方案1] 2) [方案2]

❓ [问题2] - 关于[性能/兼容性/数据]的约束
  选项: 1) [约束1] 2) [约束2]

❓ [问题3] - 关于[优先级/范围]的确认
  选项: 1) [范围1] 2) [范围2]
```

**关键原则**：
- **必须先理解现有业务**，再分析新需求
- **明确需求类型**，不同类型有不同的分析重点
- **识别与现有功能的集成点**，不是孤立的功能
- **评估对现有功能的影响**，包括接口、行为、性能
- **不假设脱离现有业务的需求细节**
- **不确定时立即询问**，提供选项让用户选择

---

### 步骤4：渐进式披露（技术细节）

**场景**：在业务上下文清晰后，按需确认技术细节。

**确认内容**：
- 实现方案偏好（在现有架构约束内）
- 性能要求（不低于现有功能基线）
- 兼容性要求（与现有功能的兼容）
- 数据迁移（如涉及现有数据变更）

**确认点**：用户确认需求理解完整准确，所有关键问题已澄清。

**确认点**：请用户确认需求卡片内容是否准确完整。

## 阶段3：Skills功能白名单检查

**目标**：确保需求涉及的Unity功能在Skills文档中有覆盖。

**操作**：
1. 分析需求卡片中涉及的所有Unity技术点
2. 逐项在Skills文档中查找对应的API白名单
3. 标记已覆盖和未覆盖的技术点

**Skills文档检查范围**：

| 技术领域 | 对应Skill | 路径 |
|---------|----------|------|
| 2D物理 | unity-2d-physics | l1-basics/ |
| Sprite精灵 | unity-2d-sprite | l1-basics/ |
| 2D动画 | unity-2d-animation | l1-basics/ |
| 瓦片地图 | unity-tilemap | l1-basics/ |
| 输入系统 | unity-input-system | l1-basics/ |
| UI系统 | unity-ui-system | l1-basics/ |
| 音频系统 | unity-audio-system | l1-basics/ |
| 场景管理 | unity-scene-management | l2-features/ |
| 预制体 | unity-prefab-system | l2-features/ |
| 状态机 | unity-state-machine | l2-features/ |
| 协程 | unity-coroutine-system | l2-features/ |
| 对象池 | unity-object-pool | l2-features/ |
| 存档 | unity-save-system | l2-features/ |
| 角色控制 | unity-2d-character-controller | l2-features/ |
| 数据配置 | unity-scriptableobject-config | l2-features/ |
| 时间轴 | unity-timeline | l2-features/ |

**输出格式**：
```
🔍 Skills白名单检查

已覆盖的技术点：
✅ [技术点1] → @unity-2d-physics（推荐API：Rigidbody2D, Collider2D）
✅ [技术点2] → @unity-ui-system（推荐API：Canvas, GridLayoutGroup）
✅ [技术点3] → @unity-object-pool（推荐API：泛型对象池）

未覆盖的技术点：
❌ [技术点4] - Skills文档中暂无对应内容
   → 建议：开发前先补充该技术点的Skills文档
   → 或：使用替代方案 [替代建议]

检查结论：[全部覆盖 / 部分未覆盖 / 大量未覆盖]
```

**未覆盖时的处理**：
- 少量未覆盖（1-2个）：标记为风险，在架构分析阶段重点关注，建议开发前查阅Unity官方文档补充
- 大量未覆盖（3+个）：暂停流程，建议先补充Skills文档再继续

**确认点**：用户确认白名单检查结果，决定是否继续。

---

## 阶段4：架构设计分析

**目标**：对需求进行架构层面的分析。

**操作**：调用 `@architecture-design-analyzer` 执行完整的5阶段架构分析。

**调用方式**：
```
@architecture-design-analyzer
需求: [需求描述]
模块: [所属模块]
复杂度: [L1/L2/A级]
```

**architecture-design-analyzer 将执行**：
1. 系统定位分析 → 用户确认模块归属
2. 设计决策建议 → 用户选择设计方案
3. 影响面评估 → 用户确认是否继续
4. 风险识别 → 用户确认风险可接受
5. 生成架构分析报告

**本阶段输出**：架构设计与影响面分析报告

**注意**：
- 本阶段由 architecture-design-analyzer Skill 主导执行
- requirement-workflow 负责触发和接收结果
- 每个确认点都需要用户参与

---

## 阶段5：影响面分析

**目标**：评估改动对现有代码的影响。

**操作**：调用 `@impact-scope-analyzer` 执行完整的影响面分析。

**调用方式**：
```
@impact-scope-analyzer
改动类型: [新增功能/修改功能/重构]
涉及文件: [预估的文件列表]
```

**impact-scope-analyzer 将执行**：
1. 识别改动范围
2. 依赖关系梳理
3. 影响面评估
4. 风险识别
5. 测试建议

**本阶段输出**：影响面分析报告（含回归测试建议）

**注意**：
- 如果是全新功能（不修改现有代码），影响面分析可简化为"确认无影响"
- 如果是修改现有功能，必须执行完整分析

---

**目标**：汇总所有分析结果，生成统一的审批报告。

**操作**：汇总前5个阶段的成果。

**审批报告模板**：
```markdown
# 需求开发审批报告

## 基本信息
- **需求名称**: [名称]
- **所属模块**: [模块]
- **分析日期**: [日期]

## 需求摘要
[一句话描述需求的核心内容]

**需求类型**: [新增功能/功能扩展/功能优化/功能重构/Bug修复]
**与现有功能的关系**: [基于[功能A]扩展 / 与[功能B]集成 / 优化[功能C]等]

## 分析结果汇总

### Context 复用
✅ 已读取项目 Context
- Context 版本: [日期]
- 涉及模块: [模块A], [模块B]
- 参考文档: [context/modules/模块A.md]

### 现有业务分析
- **相关现有功能**: [功能A], [功能B]
- **需求类型判定**: [类型] - [判定理由]
- **集成点**: 调用[接口X]，触发[事件Y]
- **对现有功能的影响**: [影响描述]

### 需求卡片
✅ 已生成 → `docs/requirements/[功能名].md`
- 包含完整的现有业务上下文分析
- 明确与现有功能的集成点

### Skills白名单检查
- 已覆盖技术点: [X]个
```

## 与其他Skill的关系

```
requirement-workflow（编排器）
    ├── 检查/触发 → project-context-analyzer（B级）⭐ 新增
    │       ├── 检查 context/ 是否存在
    │       ├── 不存在 → 提示用户调用本 Skill 沉淀
    │       └── 存在 → 读取并引用 Context
    │
    ├── 触发 → architecture-design-analyzer（B级）
    ├── 触发 → impact-scope-analyzer（B级）
    ├── 检查 → unity-2d-game-development/*（L1/L2级，白名单）
    ├── 检查 → unity-design-patterns/*（L1/L2级，设计模式参考）
    └── 输出为 → 开发阶段的输入
                  └── 开发完成后 → unity-code-review（C级）
```

**Context 流转**：
```
project-context-analyzer
    └── 生成 → context/ 目录
            └── 被 requirement-workflow 读取
                    └── 被 architecture-design-analyzer 引用（架构决策参考）
                    └── 被 impact-scope-analyzer 引用（依赖关系参考）
```

**不替代其他Skill**：本Skill是流程编排器，不替代 architecture-design-analyzer 和 impact-scope-analyzer 的具体分析能力，而是负责串联和引导。

## 注意事项

1. **渐进式披露贯穿始终**：每个阶段都必须等待用户确认后再进入下一步
2. **白名单检查是核心机制**：确保开发只使用Skills文档中已覆盖的API，避免引入未知风险
3. **不可跳过架构分析**：即使是快速模式，架构分析（阶段4-5）也不可跳过
4. **审批报告是开发依据**：审批通过后，报告中的"建议Skills使用清单"和"开发优先级"是开发阶段的输入
5. **本Skill是强制规范的一部分**，不可跳过
