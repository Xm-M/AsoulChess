# 开发执行工作流

## 目的

作为开发执行的主 Agent，负责：
1. 调用功能拆分器生成可执行的功能列表
2. 管理增量开发循环
3. 协调子 Agents（代码生成、审查、**编译验证**、自动修复）
4. 跟踪和报告开发进度

**核心原则**：增量式开发，一次只完成一个功能；**编译错误在进Unity前必须解决**。

## 使用场景

**启动新开发**：
```
@development-workflow start
需求: [需求ID]
```

**继续开发**：
```
@development-workflow continue
需求: [需求ID]
```

**开发特定功能**：
```
@development-workflow dev
需求: [需求ID]
功能: [功能ID]
```

## 工作流程

```
接收到开发指令
    ↓
阶段1: 检查需求状态
    ↓
阶段2: 功能列表生成/检查
    ├── 不存在 → 调用 @feature-decomposer
    └── 存在 → 读取现有功能列表
    ↓
阶段3: 开发准备
    ├── 调用 @progress-recovery 恢复状态
    └── 选择要开发的功能
    ↓
阶段4: 增量开发循环 ⭐ 新增编译验证
    ├── 加载功能上下文
    ├── 调用 @code-generator 生成代码
    ├── 调用 @unity-code-validator 编译验证  ← 新增 ⭐
    │   ├── 通过 → 继续
    │   └── 失败 → 自动修复循环
    ├── 调用 @code-reviewer 代码审查
    └── 更新功能状态
    ↓
阶段5: 开发完成处理
    ├── 生成总结报告
    └── 建议下一步
```

## 阶段4: 增量开发循环（含编译验证）

### 4.1 编译验证机制 ⭐ 核心新增

**目标**：确保AI生成的代码在Unity外部就通过编译检查，避免延迟发现错误。

**触发时机**：每次 `@code-generator` 生成代码后，立即执行编译验证。

**验证流程**：

```
代码生成完成
    ↓
调用 @unity-code-validator
    ↓
预防层检查
    ├── 命名空间声明检查
    ├── MonoBehaviour继承检查
    └── Unity API规范检查
    ↓
检测层验证
    ├── Roslyn分析器检查
    ├── dotnet build编译检查
    └── SARIF错误解析
    ↓
检查结果?
    ├── ✅ 通过 → 进入代码审查
    └── ❌ 失败 → 修复循环
```

### 4.2 自动修复循环

**场景**：编译验证发现错误时，自动进入修复流程。

**修复流程**：

```
发现编译错误
    ↓
AI分析错误原因
    ↓
生成修复方案
    ↓
应用修复
    ↓
重新编译验证
    ↓
检查结果?
    ├── ✅ 通过 → 完成修复
    ├── ❌ 失败且次数<3 → 继续修复循环
    └── ❌ 失败且次数≥3 → 人工介入
```

**修复限制**：
- 最多尝试 3 次自动修复
- 第 3 次失败后，停止自动修复，报告给用户
- 用户可以选择：人工修复 / 跳过 / 重新生成

### 4.3 代码生成器集成规范

**调用 `@code-generator` 时必须传递编译约束**：

```markdown
## 代码生成约束（强制执行）

生成代码前，请确认以下检查清单：

### 基础结构
- [ ] 类名与文件名完全一致（区分大小写）
- [ ] 类声明使用public访问修饰符
- [ ] 组件脚本显式继承`: MonoBehaviour`

### 命名空间
- [ ] 包含 `using UnityEngine;`
- [ ] 如使用UI组件，包含 `using UnityEngine.UI;` 或 `using UnityEngine.UIElements;`

### 生命周期方法
- [ ] Awake() 方法签名：`private void Awake()`
- [ ] Start() 方法签名：`private void Start()`
- [ ] Update() 方法签名：`private void Update()`

### Unity约束
- [ ] 禁止使用new创建MonoBehaviour（使用AddComponent）
- [ ] 避免在构造函数中使用Unity API
- [ ] 类名必须与文件名一致

**生成后自动执行编译验证**。
```

## 阶段4详细流程

### 4.4 单次功能开发流程

```
开始功能: [功能ID]
    ↓
步骤1: 加载上下文
    ├── 读取需求卡片
    ├── 读取架构设计
    └── 读取相关模块代码
    ↓
步骤2: 代码生成
    ├── 调用 @code-generator
    ├── 传递编译约束Prompt
    └── 获取生成的代码
    ↓
步骤3: 编译验证 ⭐
    ├── 调用 @unity-code-validator
    ├── 执行预防层检查
    ├── 执行检测层验证
    └── 获取验证报告

    ├── ✅ 无编译错误
    │       └── 继续步骤5
    └── ❌ 发现编译错误
            ├── 尝试自动修复（最多3次）
            ├── 修复后重新验证
            └── 修复失败 → 报告用户
    ↓
步骤5: 代码审查
    ├── 调用 @code-reviewer
    ├── 检查代码质量
    └── 检查设计规范
    ↓
步骤6: 更新功能状态
    ├── 标记功能完成
    ├── 记录开发日志
    └── 保存代码到项目
    ↓
功能开发完成
```

## 编译验证失败处理

### 场景1: 单次错误，自动修复成功

```
❌ 编译验证失败

错误信息:
- 错误1: CS0103 名称"playerHealth"不存在于当前上下文
- 位置: PlayerController.cs:42

AI分析: 变量名拼写错误，应为"PlayerHealth"（大写P）

修复方案:
- 将playerHealth改为PlayerHealth

✅ 重新验证通过
```

### 场景2: 多次错误，需要人工介入

```
❌ 编译验证失败（第3次尝试）

剩余错误:
- 错误1: CS0246 找不到类型或命名空间"InventoryManager"
- 错误2: CS0103 名称"SaveSystem"不存在

AI分析: 缺少依赖类定义，可能是功能拆分导致的依赖问题。

建议方案:
1. 先开发 InventoryManager 类（功能 INV-003）
2. 或在此功能中包含 InventoryManager 的基础定义
3. 或调整功能拆分顺序

请选择：
[A] 调整开发顺序，先开发依赖功能
[B] 在此功能中添加依赖类的基础定义
[C] 跳过编译验证，继续开发（不推荐）
```

## 工具调用规范

### 调用 @unity-code-validator

**时机**：代码生成后、代码审查前

**参数**：
```yaml
代码: [生成的C#代码]
项目路径: [Unity项目路径]
Unity版本: [如 2022.3]
检查级别: [严格/标准/宽松]
```

**输出解析**：
- 预防层报告：检查清单通过情况
- 检测层报告：编译错误列表（SARIF格式）
- 修复建议：AI生成的修复方案

## 与现有流程的对比

| 环节 | 原流程 | 新流程（含编译验证） |
|------|--------|---------------------|
| 代码生成 | 直接生成 | 生成 + 约束检查清单 |
| 验证时机 | 进Unity后 | **生成后立即验证** |
| 错误发现 | 人工在Unity中发现 | **AI自动检测** |
| 错误修复 | 人工修复或反馈给AI | **AI自动修复（3次尝试）** |
| 开发效率 | 反复切换Unity | **闭环验证，一次通过** |

## 快速使用指南

### 启动开发（自动包含编译验证）

```
@development-workflow start
需求: inventory-system
```

**AI行为**：
1. 检查需求审批状态
2. 生成功能列表
3. 开始第一个功能的开发
4. **每个功能生成后自动编译验证**
5. 如有错误自动修复
6. 通过后进入代码审查

### 跳过编译验证（不推荐）

```
@development-workflow start
需求: inventory-system
编译验证: 跳过
```

**警告**：跳过编译验证可能导致代码进入Unity后才发现错误。

## 配置要求

### 环境准备

```bash
# 1. 安装 .NET SDK（用于编译检查）
# 下载地址: https://dotnet.microsoft.com/download

# 2. 安装 Roslynator CLI
dotnet tool install -g roslynator.dotnet.cli

# 3. 在Unity项目中添加分析器
# 通过Package Manager添加 Microsoft.Unity.Analyzers
```

### 项目配置

```xml
<!-- 在项目 .csproj 中添加 -->
<ItemGroup>
  <PackageReference Include="Microsoft.Unity.Analyzers" Version="1.26.0" />
</ItemGroup>
```

## 常见问题

**Q: 编译验证会增加多少开发时间？**
A: 首次配置约10分钟，后续每个功能增加30秒-2分钟（取决于是否需要自动修复）。但能节省在Unity中反复发现和修复错误的时间。

**Q: 自动修复安全吗？**
A: 自动修复仅限于明确的编译错误（如拼写错误、缺少分号、命名空间缺失等）。AI会先生成修复方案并展示，用户可以选择是否应用。

**Q: 如果自动修复失败怎么办？**
A: 3次尝试后AI会停止自动修复，提供详细的错误分析和建议方案，由用户决定如何处理。

**Q: 所有项目都需要编译验证吗？**
A: 推荐所有Unity项目启用。对于简单功能（<50行代码），可以在Prompt中明确要求AI自查，跳过正式的编译验证。
