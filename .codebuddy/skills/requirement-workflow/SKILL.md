# 需求开发流程

## 适用场景

**强制使用**：新功能开发、修改核心系统、跨模块功能
**可选使用**：简单功能（<50行）、独立工具类
**豁免**：Bug修复（<10行）、配置调整、UI文案修改、纯资源替换

## 流程总览

```
用户提出需求
  │
  ▼
阶段1: Context 读取 + 现有业务分析
  │
  ▼
阶段2: 需求理解 + 信息缺口识别（渐进式披露）
  │
  ▼
阶段3: 生成需求卡片
  │
  ▼
阶段4: 架构设计分析
  │
  ▼
阶段5: 影响面分析
  │
  ▼
阶段6: 审批报告 → 用户决策
  │
  ├── 通过 → 进入开发
  ├── 修改后通过 → 回到阶段2
  └── 驳回 → 终止
```

---

## 阶段1: Context 读取与现有业务分析

读取 `asoulchess-context` skill 的 references 目录，分析需求涉及的模块。

### 操作步骤

1. 根据需求识别相关模块，加载对应参考文档：
   - `references/GameManage.md` - 管理器模块
   - `references/ChessSystem.md` - 棋子系统
   - `references/Buff.md` - Buff系统
   - `references/Event.md` - 事件系统
   - `references/FetterSystem.md` - 羁绊系统
   - `references/LevelSystem.md` - 关卡系统
   - `references/SaveSystem.md` - 存档系统
   - `references/UISystem.md` - UI系统
   - `references/decisions.md` - 架构决策
   - `references/dependency-graph.md` - 依赖关系

2. 输出现有业务分析：

```
现有业务分析:
- 目标模块: [模块名]
- 模块现状: [现有核心功能列表]
- 公共接口: [关键接口]
- 功能相似性: [是否有类似功能可复用]
- 依赖关系: [上下游依赖]
- 架构约束: [设计模式限制、性能基线]
```

3. 判定需求类型：

| 类型 | 定义 | 分析重点 |
|------|------|----------|
| 新增功能 | 全新模块/机制 | 与现有架构的兼容性 |
| 功能扩展 | 现有模块新增能力 | 接口兼容性 |
| 功能优化 | 改进体验/性能 | 回归风险 |
| 功能重构 | 重写但行为不变 | 行为一致性 |
| Bug修复 | 修复缺陷 | 修复范围 |

---

## 阶段2: 需求理解（渐进式披露）

在理解现有业务基础上分析新需求。

### 分析框架

新需求必须回答：

1. **业务价值**: 解决什么痛点？提升什么指标？
2. **集成点**: 调用哪些现有接口？触发哪些事件？
3. **变更点**: 接口变化？行为变化？数据格式变化？
4. **依赖**: 需要现有模块提供什么新支持？
5. **约束**: 性能不能下降？兼容性要求？

### 输出格式

```
需求理解确认:
- 功能目标: [一句话描述]
- 业务价值: [解决什么问题]
- 调用的现有接口: [列表]
- 触发的现有事件: [列表]
- 对现有功能的影响: [变更说明]
- 需要澄清的问题: [选项式提问]
```

**确认点**: 等待用户确认需求理解完整准确。

---

## 阶段3: 生成需求卡片

按照以下模板生成需求卡片，保存到 `docs/requirements/[功能名].md`。

### 需求卡片模板

```markdown
# 功能需求卡片: [功能名称]

## 基本信息
- 功能名称: [名称]
- 所属模块: [模块]
- 需求类型: [新增/扩展/优化/重构/Bug修复]
- 优先级: [P0/P1/P2]
- 预估耗时: [X小时]
- 提出日期: [YYYY-MM-DD]

## 功能描述
[详细描述]

## 现有业务上下文
### 相关现有功能
| 功能 | 模块 | 关系 | 说明 |
|------|------|------|------|

### 集成点
- 调用的现有接口: [列表]
- 触发的现有事件: [列表]

### 对现有功能的影响
- 接口变更: [说明]
- 行为变更: [说明]

## 功能清单
### 核心（必须）
- [ ] [功能1]

### 扩展（可选）
- [ ] [功能2]

## 验收标准
- [ ] 功能实现完整
- [ ] 性能达标
- [ ] 代码通过审查
```

**确认点**: 请用户确认需求卡片内容。

---

## 阶段4: 架构设计分析

### 分析步骤

1. **系统定位**: 需求属于哪个模块？是否需要新建模块？
2. **设计决策**: 推荐的设计方案，参考项目现有模式：
   - 新功能优先通过 EventController 通信
   - 棋子新能力通过继承 Controller 实现
   - 数据配置使用 ScriptableObject
   - UI面板继承 View 基类
   - 尽量不新增 MonoBehaviour，优先继承/组合
3. **扩展方式**: 选择正确的扩展路径
4. **风险识别**: 循环依赖、性能、内存泄漏
5. **实现约束**: 必须复用现有框架内代码

### 架构分析输出

```
架构设计分析:
- 系统定位: [模块归属]
- 设计方案: [推荐方案 + 理由]
- 扩展方式: [继承/组合/新增]
- 关键类: [涉及的类和修改点]
- 事件设计: [需要的事件]
- 数据结构: [需要的数据类]
- 风险评估: [风险点和应对]
```

**确认点**: 等待用户确认架构方案。

---

## 阶段5: 影响面分析

### 分析维度

| 维度 | 检查项 |
|------|--------|
| 文件影响 | 新增/修改哪些文件 |
| 接口影响 | 现有接口是否变更 |
| 依赖影响 | 哪些模块受到影响 |
| 数据影响 | 存档结构是否变更 |
| 性能影响 | 是否影响帧率/内存 |
| UI影响 | 是否影响现有UI |

### 输出格式

```
影响面分析:
- 影响文件数: [X]个
- 新增文件: [列表]
- 修改文件: [列表]
- 高风险点: [列表]
- 回归测试项: [列表]
- 结论: [可继续/需关注/风险较高]
```

---

## 阶段6: 审批报告

汇总所有分析，生成审批报告：

```
审批报告
========
需求名称: [名称]
需求类型: [类型]

分析结果:
- Context: 已读取
- 需求卡片: docs/requirements/[名称].md
- 架构方案: [摘要]
- 影响文件: [X]个
- 高风险点: [X]个

风险总评:
| 维度 | 评级 | 说明 |
|------|------|------|
| 技术可行性 | [高/中/低] | |
| 改动范围 | [大/中/小] | |
| 性能风险 | [高/中/低] | |

决策: [通过 / 修改后通过 / 驳回]
```

**确认点**: 等待用户做出最终审批决策。

---

## 审批通过后

```
审批通过！
已生成文档:
- 需求卡片: docs/requirements/[名称].md

下一步: 按功能清单优先级逐项实现
开发完成后: 执行代码审查（性能、安全、最佳实践）
```

## 快速模式

当用户已提供完整需求（明确描述 + 模块 + 约束 + 验收标准）时，可简化阶段1-2，直接确认理解后进入阶段3。

快速模式不跳过架构分析（阶段4）和影响面分析（阶段5）。
